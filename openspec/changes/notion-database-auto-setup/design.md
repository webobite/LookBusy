# Design

## Context

- All Notion access lives in `src/notion.ts`: `logSession` makes one `fetch` to `POST /v1/pages` with `Notion-Version: 2022-06-28`, and `buildPagePayload` hard-codes `Name`, `Date`, `Session Type` and `Status`.
- The service worker (`src/background.ts`) owns `TimerState`, which includes `task`, in `chrome.storage.local`. It builds a `CompletedSession` when an interval ends and calls `logSession`. The popup updates the task via the `setTask` message.
- Session-type labels come from `SESSION_TYPES` in `src/constants.ts`.
- `options.ts` reads and writes `Settings` in `chrome.storage.sync`. It runs as an extension page and can call `api.notion.com` under the existing `host_permissions`.
- The project has no test runner. Verification today is `npm run typecheck`, `npm run build` and loading `dist/` in Chrome.
- Notion constraints:
  - An internal integration can only create databases under a page shared with it.
  - On `2022-06-28`, a two-way relation's property on the other database gets a default name, `Related to …`.
  - Rich-text content is limited to 2000 characters per text object.

## Goals / Non-Goals

**Goals:**
- One source of truth for both schemas, used by creation, logging and the approval summary.
- Daily focus counts that Notion computes itself and that stay correct when rows are edited.
- No new permissions. Users on the old schema keep logging without doing anything.

**Non-Goals:**
- Moving to Notion API `2025-09-03` (data sources).
- Migrating `v1` databases to `v2`, or checking a manual database beyond detecting its version.
- Back-filling streaks or day links for past rows. Syncing the streak across devices.

## Decisions

### 1. `src/schema.ts` holds both schemas
It exports:
- The property names for sessions (`v2` and `v1`) and for the daily database.
- The database titles.
- The `Completed` value.
- The `Focus Count` formula expression: `if(prop("Session Type") == "Focus", 1, 0)`.

It also provides `describeSchemas()`, which returns column/type/options rows for the approval dialog. Select options come from `SESSION_TYPES`.

*Alternative:* literals spread across modules. Rejected: schema drift is the failure this change removes.

### 2. Creation sequence (options page)
1. `POST /v1/databases`: create **Sessions** under the parent with every property except `Day`.
2. `POST /v1/databases`: create **Daily Summary** with `Day`, `Date` and `Sessions` (a two-way relation to Sessions, `dual_property: {}`).
3. `PATCH /v1/databases/{daily}`: add the `Focus Pomodoros` rollup (`Sessions` → `Focus Count`, `sum`) and the `Total Sessions` rollup (`Sessions` → `Task`, `count`). This is a separate step so that the relation already exists when the rollups refer to it.
4. `PATCH /v1/databases/{sessions}`: rename the synced relation property, found by the `dual_property.synced_property_id` in step 2's response, to `Day`.

If any step after step 1 fails, delete what was created with `DELETE /v1/blocks/{id}`, which moves a database to Notion's trash. Delete the daily database first, then sessions. If that cleanup also fails, show which database is left over. Save settings only after step 4 succeeds, as one `chrome.storage.sync.set({ notionToken, databaseId, dailyDatabaseId, schemaVersion: 'v2' })`.

*Alternative:* create Daily first and put the relation on Sessions. Same number of calls, but Sessions is the database users care about most, so building it first gives clearer errors.

### 3. Parent page discovery via `POST /v1/search`
- Filter on `object = page` and paginate up to 100 results.
- Drop pages with `parent.type === 'database_id'`, which are database rows.
- A page's title comes from its `title`-type property, with `Untitled` as a fallback.
- Show the pages in a `<select>`, with a paste-a-page-URL fallback.
- `parseDatabaseId` becomes `parseNotionId` and is reused for that fallback.

### 4. Approval with a native `<dialog>`
The dialog shows the parent page, both titles and one table per database, generated by `describeSchemas()`. It has **Create** and **Cancel** buttons. `window.confirm` cannot render the tables.

### 5. One-time guard has three layers
1. The UI hides the action when a sessions `databaseId` is set.
2. An in-flight flag disables **Create** from the first click.
3. Storage is re-read just before step 1, and setup aborts if a `databaseId` has appeared.

### 6. Description travels with the task
- Add `description` to `TimerState` and `CompletedSession`, and a `{ action: 'setDescription'; description }` `WorkerRequest`, mirroring `setTask`.
- The popup gets a `<textarea id="description">`.
- Like the task, the description persists across intervals until the user changes it.
- It is truncated to 2000 characters when logged.

### 7. The streak is computed locally in the worker
- Add a pure function `nextStreak(prev: { lastFocusDay, streak }, today, isFocus)` in `src/streak.ts`.
- `localDay(ts)` formats a timestamp as `YYYY-MM-DD` in local time.
- When an interval completes, the worker updates `{ lastFocusDay, streak }` in `chrome.storage.local` (Focus only), then logs with the resulting value.
- For a break, the logged value is: the stored streak if `lastFocusDay` is today or yesterday, otherwise 0.
- The streak is updated whether or not the Notion write succeeds, because it reflects completed work, not log success.

*Alternative:* compute it from the Daily Summary in Notion. Rejected: it adds a query per session and fails offline.

### 8. Day row find-or-create in `logSession`
- Cache `{ dailyDatabaseId, day, pageId }` for the last day used in `chrome.storage.local`.
- On a cache miss, run `POST /v1/databases/{daily}/query` with a filter on `Date` equal to the day. If there is no result, create the row.
- If creating the session fails with a validation error while it carries a cached `Day`, clear the cache and retry once. This covers a day row the user deleted.
- If day linking fails, log the session without `Day` (see spec).

### 9. Schema version detection
- `Settings` gains `dailyDatabaseId: string` and `schemaVersion: 'v1' | 'v2'`, both read through `getSettings()` defaults; the default version is `v1`.
- When Settings is saved, `options.ts` calls `GET /v1/databases/{id}` and applies the rule in the spec.
- `buildPagePayload` branches on the version, and the `v1` branch reproduces today's payload byte for byte.

### 10. Device identity is stored only on the device
- `deviceName` and `deviceId` live in `chrome.storage.local`, not in `Settings`. `storage.sync` would copy one name to every computer on the Chrome profile, which defeats the column.
- `deviceId` is `crypto.randomUUID()`, generated on the first save that has a name.
- `options.ts` requires a trimmed, non-empty name to save, and to enable "Create databases for me".
- The worker reads both when logging a `v2` row and writes them as `Device` (`select: { name }`) and `Device ID` (rich text).
- Notion adds a new select option automatically the first time a name is written. That needs no extra permission, because the integration already edits the database.

*Alternative:* `Device` as text. Rejected: a select gives filter and group chips in Notion, which the user chose.

### 11. Device rename runs as a resumable job in the service worker
- On Save, if the name changed and `schemaVersion` is `v2`, `options.ts` writes `pendingRename = { deviceId, name, updated: 0 }` to `chrome.storage.local` and sends a `{ action: 'applyRename' }` message.
- A second rename overwrites `name` in place, so the job always converges on the latest name.
- The worker loop:
  1. Query the sessions database with a filter on `Device ID` equal to `deviceId` **and** `Device` not equal to `name`, 100 rows per page.
  2. `PATCH /v1/pages/{id}` each row with the new `Device` select, about 3 requests per second, increasing `updated` as it goes.
  3. Re-query from the start until the query returns nothing, then delete `pendingRename`.
- Filtering on "not already renamed" makes the job idempotent. Re-running it after a crash only touches rows that are still stale, so no cursor needs to survive a restart.
- For resuming:
  - `chrome.runtime.onStartup` and a `lookbusy-rename` alarm (every 1 minute while `pendingRename` exists) restart the loop.
  - A worker-level flag stops two loops running at once.
  - On a 429 response, wait for `Retry-After`. On other errors, stop until the next alarm.
- Settings shows progress by listening to `chrome.storage.onChanged` for `pendingRename`.
- The rename leaves old select options in the database's option list. They are harmless, so no cleanup is attempted.

*Alternatives:*
- Rename the select option itself with one schema PATCH. Rejected: the 2022-06-28 API does not support renaming existing options, and other devices could share that option.
- Run the job in the options page. Rejected: closing the tab would stop it.
- Match rows by old name. Rejected by the user in favour of `Device ID`.

### 12. Shared `notionFetch` and tests
- `notionFetch(token, method, path, body?)` centralises headers and error parsing for every call.
- `npm test` runs `npm run build && node --test test/`, with `test/*.test.mjs` importing from `dist/src/`.
- The tests cover:
  - The `v1` payload is unchanged.
  - The `v2` payload uses the schema names.
  - The database payloads match the page payloads.
  - The `nextStreak` and `localDay` edge cases.
  - The `v2` payload carries `Device` and `Device ID`.
  - The rename query filter is built correctly.

## Risks / Trade-offs

- [Notion rejects creating a rollup and its relation in one flow, or names the synced property differently] → Steps 3 and 4 run as separate PATCHes, keyed by property ID rather than name.
- [Logging now takes up to three requests when the day is not cached] → The day cache makes it one request for every session after the first each day.
- [Day rows duplicated across devices on the same date] → The query-first approach makes this rare. A duplicate splits that day's counts, which can be fixed by merging in Notion.
- [The streak is per device, because `storage.local` doesn't sync] → Documented in the README. Syncing the streak is out of scope.
- [Local-date boundaries shift after a timezone change while travelling] → Accepted. Days follow the device's clock at completion time.
- [A rename over a large history (thousands of rows) takes many minutes and consumes the rate limit] → The job is paced and resumable. Logging new sessions keeps working while it runs, because a 429 on a log is reported like any other logging error.
- [The user edits `Device ID` by hand in Notion] → Those rows drop out of future renames. The README documents the column as managed by the extension.
- [`2022-06-28` database creation deprecated in favour of data sources] → All version-specific code sits behind `notionFetch` and the payload builders.

## Migration Plan

This is additive:
- Existing users have no `schemaVersion`, so they are treated as `v1` and log exactly as before.
- Existing users are asked for a device name the next time they save Settings. It has no effect on `v1` logging.
- Re-saving Settings runs detection.
- To get the new schema, a user clears the database ID and runs setup. The old database stays as an archive in Notion.

Rollback means reverting the commit. The new storage keys are ignored by older builds.
